# RelayDock v0.5.0 delivery scope

This document is the frozen delivery contract for the next RelayDock release.
Implementation, review, packaging, and release verification must use these
acceptance criteria. Items must not be described as working until their checks
pass on a clean macOS user account.

## 1. Keychain stability

- RelayDock must not show a Keychain password dialog merely because the app was
  updated, launched, an endpoint card was selected, or a model check was run.
- All background credential reads must explicitly disallow authentication UI.
  An inaccessible legacy item is treated as unavailable and the UI asks the
  user to enter that endpoint's key again without triggering a system dialog.
- The local self-signing workflow must preserve its existing signing identity.
  A partial or damaged signing setup must fail with repair instructions instead
  of silently rotating the identity and invalidating existing Keychain ACLs.
- A credential entered once must remain usable without repeated prompts during
  normal operation. Credential values must never be passed on a process command
  line, written to logs, or stored in RelayDock configuration as plaintext.
- Update, reinstall, signing, and uninstall paths must each be tested. The
  uninstaller removes only RelayDock-owned Keychain items.

## 2. Endpoint and profile management

- A RelayDock configuration can contain multiple independent endpoints. Each
  endpoint has its own display name, protocol/provider type, base URL, API key,
  enabled state, and discovered/verified model list.
- OpenAI-compatible, Azure OpenAI-compatible, and Anthropic-compatible routes
  can coexist. Adding or editing one endpoint must not overwrite another.
- The initial built-in endpoint is displayed as **Gateway 1**, not **Sub2API**.
  Existing user-created endpoint names are preserved exactly and are never
  renamed during migration.
- Endpoint tests authenticate with that endpoint's own key, discover models
  when the provider exposes a model-list API, and persist the result only after
  a successful, protocol-appropriate response.
- Common-provider shortcuts for OpenAI/ChatGPT API, Kimi, and Volcengine Ark may
  prefill supported public endpoint/protocol fields, but they must be described
  as connection/configuration helpers—not subscription purchase, account
  billing, or OAuth. Users provide any required API endpoint, deployment name,
  and token explicitly; RelayDock does not claim access to consumer chat-plan
  entitlements.
- Endpoint keys remain in Keychain and are never serialized into the ordinary
  profile configuration. Provider shortcuts must not weaken this rule.

## 3. Cursor one-click configuration and launch

RelayDock must configure Cursor before launching it, with explicit endpoint
selection when more than one RelayDock endpoint can serve a protocol.

### OpenAI-compatible models

- Write the selected RelayDock endpoint into Cursor's **Override OpenAI Base
  URL** setting and write its API key into Cursor's OpenAI key storage path.
- Enable Cursor's OpenAI-key mode and make the selected, verified models
  available through that route.
- Do not pass the key in launch arguments. Use a version-checked, transactional
  configuration import with a minimal rollback snapshot.

### Anthropic models

- Write only the selected RelayDock endpoint's API key into Cursor's Anthropic
  key storage path and enable Cursor's Anthropic-key mode.
- Cursor's fixed `api.anthropic.com` destination is handled by RelayDock's local
  bridge. The bridge terminates TLS only for `api.anthropic.com`, replaces the
  upstream endpoint and authentication with the selected RelayDock Anthropic
  route, and preserves streaming responses.
- Use a domain-scoped trusted leaf certificate with SAN
  `api.anthropic.com`, `CA:FALSE`, and server-auth usage. It must not be a root
  CA and must not be capable of signing certificates for other domains.
- Non-target proxy traffic remains an unmodified byte tunnel. The listener is
  loopback-only; request bodies, responses, and credentials are never logged.
- The functional Bridge accepts only the explicit Anthropic message POST
  routes used by Cursor and requires the incoming endpoint key before injecting
  upstream authentication; discovering its random loopback port is not enough
  to consume the user's gateway quota.
- Certificate installation is a deliberate one-click setup action with clear
  system authorization copy. RelayDock provides one-click removal, and the app
  uninstaller removes the certificate, private key, trust entry, bridge files,
  and RelayDock-owned proxy settings.

### Safe import lifecycle

- Require Cursor to be fully quit before import. Detect the supported Cursor
  database/schema version before changing anything.
- Snapshot only affected Cursor settings and key records, protect the snapshot
  with mode `0600`, then mutate them in one SQLite transaction.
- Launch Cursor only after configuration, certificate, bridge, and proxy checks
  pass. Verify Cursor migrated temporary legacy key records into its encrypted
  secret storage; remove any remaining plaintext record.
- On any failure, stop the bridge and restore the snapshot. The UI must report
  the failed stage and must never say “connected” based only on a process launch.
- Clearly distinguish the diagnostic **Probe** mode from the functional
  **Sub2API Bridge** mode.

## 4. OpenCode one-click configuration and launch

- Generate an isolated OpenCode configuration containing every enabled
  RelayDock endpoint, its protocol, and only its verified model list.
- Reference keys through RelayDock-owned files with mode `0600`; do not embed
  keys directly in JSON or shell arguments.
- One click performs validation, writes the configuration atomically, and
  launches OpenCode with that configuration. Existing global/project OpenCode
  configuration is not overwritten.
- The UI and documentation consistently call this a Sub2API connection. “Serper
  API” is not part of this release scope.

## 5. Model discovery and verification

- A successful endpoint test automatically discovers its advertised models.
- “Test models” performs a real protocol-appropriate request for every selected
  model, with bounded concurrency and an actionable result for each model.
- Models rejected definitively as unknown, missing, or unsupported are removed
  from the usable list and the new list is persisted.
- Authentication failures, rate limits, network failures, and server errors are
  retained and reported as transient/configuration failures; they must not cause
  a destructive mass removal.
- Cursor and OpenCode import only the resulting verified model list.

## 6. Product interface and status feedback

- Endpoint management uses a restrained macOS-style interface: white,
  lightweight cards, neutral typography, minimal decoration, and no saturated
  colored card backgrounds.
- Cursor and OpenCode each have a clearly labeled one-click configure-and-open
  action. The action reports configuration, bridge, launch, and verification
  failures separately instead of treating application launch as success.
- Model discovery and model verification have visible progress and final
  results. Removed models and retained transient failures are understandable to
  the user.
- Update checking always shows its final state in the interface; the update
  button is enabled only when there is an installable release and performs the
  real install workflow rather than merely opening a download page.
- The app icon and installer presentation remain minimal and macOS-appropriate,
  using the approved restrained black/white/gray with a small orange accent.

## 7. Updates, installation, and removal

- **Check for Updates** always ends with a visible result: update available,
  already current, network failure, or invalid release.
- **Update Now** downloads the expected GitHub release asset, verifies its
  identity/integrity, installs it, relaunches it, and confirms the installed
  version. Failure leaves the current app usable and provides recovery steps.
- Updating must preserve the local signing identity and must not cause repeated
  Keychain prompts.
- English and Chinese installation instructions cover the fastest install path,
  Gatekeeper/self-signing behavior, certificate authorization, update behavior,
  and complete one-click uninstall.
- The release contains a usable macOS installer/package and the repository's
  one-command installation path remains accurate for that asset.
- Installation instructions are available in both English and Chinese and are
  included in the disk image as well as linked from the repository README.
- Gatekeeper recovery is reduced to the smallest honest number of steps. When
  an ad-hoc/local signature is required, the release includes a guided script;
  it must not promise to eliminate macOS authorization dialogs that the app
  cannot legitimately suppress.
- Uninstall removes RelayDock, its launch/configuration files, proxy process,
  domain certificate trust, certificate/private-key material, and
  RelayDock-owned Keychain entries without deleting unrelated Cursor/OpenCode
  data.

## 8. Release gate

- Automated unit/integration tests, a clean release build, installer smoke test,
  update-from-previous-version test, and uninstall test must pass.
- Manual smoke tests cover at least one OpenAI-compatible model and one Anthropic
  model in Cursor, plus a generated multi-endpoint OpenCode configuration.
- A separate subagent performs an independent security and correctness review.
  All blocking findings are fixed and re-reviewed before any commit, push, tag,
  GitHub release, or installer publication.
- Publishing requires explicit user authorization after the review report.

## Final interpretation

This scope is the agreed v0.5.0 definition of done. In particular, the local
proxy is not merely diagnostic: it is the functional bridge required for
Cursor's fixed Anthropic destination. OpenAI-compatible Cursor traffic uses
Cursor's supported override fields; Anthropic Cursor traffic uses its key field
plus RelayDock's domain-scoped TLS bridge; OpenCode uses RelayDock's isolated
multi-endpoint configuration. These decisions are frozen for this release and
must not be replaced by a manual-settings-only workflow during implementation.
